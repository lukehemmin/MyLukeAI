# 서비스 디자인정의서 v0.1

## 1. 문서 개요

- **문서명**: 실행형 AI 개발 플랫폼 서비스 디자인정의서
- **버전**: v0.1
- **목적**: 사용자용 제품 화면의 비주얼 방향, 레이아웃 원칙, 화면별 UX 중심축, 상태 표현, 반응형 원칙을 정의하여 디자인 AI 또는 실제 디자이너가 일관된 결과물을 만들 수 있게 한다.
- **관련 문서**: `docs/product-vision-v0.1.md`, `docs/screen-list-definition-v0.2.md`, `docs/computer-browser-agent-lifecycle-v0.1.md`, `docs/domain-model-erd-v0.1.md`, `docs/admin-design-definition-v0.1.md`

---

## 2. 디자인 목표

이 서비스는 단순한 AI 채팅 앱처럼 보이면 안 된다. 핵심은 `AI가 실제로 일하고`, `사용자가 그 과정을 본다`는 점이다.

따라서 디자인 목표는 다음과 같다.

- 일반 AI 채팅 서비스보다 더 `실행형`, `프로젝트 중심`, `브라우저 기반`으로 느껴져야 한다.
- OpenWebUI식 멀티 모델 채팅의 친숙함은 유지하되, Manus/Z.ai 같은 `작업 수행감`을 더 강하게 전달해야 한다.
- 채팅, 프로젝트, 브라우저, 터미널, 문서가 하나의 워크스페이스 안에서 자연스럽게 연결돼 보여야 한다.
- 기술적이지만 차갑지 않고, 고급스럽지만 과장되지 않은 UI를 목표로 한다.
- 개인 사용자에게는 직관적이고, 팀에는 협업 친화적이며, 엔터프라이즈에는 신뢰와 통제 가능성이 읽히는 UX여야 한다.

### 문서 범위

- 이 문서는 사용자용 product app 화면을 다룬다.
- 관리자 콘솔 디자인은 `docs/admin-design-definition-v0.1.md`를 canonical guide로 사용한다.
- 전체 제품 디자인 리뷰 시에는 두 문서를 함께 봐야 한다.

## 3. 제품 인상 키워드

- Visible Execution
- Project-Centric
- Technical Warmth
- Trust Through Process
- Collaborative Build Space
- Browser-Grounded

### 피해야 할 인상

- 단순 ChatGPT 클론처럼 보이는 화면
- 흔한 흰 배경 + 회색 사이드바 + 보라색 버튼 SaaS 레이아웃
- 채팅과 프로젝트가 분리되어 따로 노는 느낌
- 실행 과정이 안 보이고 결과만 보여주는 느낌

## 4. 비주얼 방향

### 4.1 전체 컨셉

제품은 `AI 대화창`보다 `AI 작업실` 또는 `AI 개발 워크스페이스`처럼 보여야 한다.

추천 분위기:

- 정돈된 실험실
- 공방 같은 제작 공간
- 브라우저와 코드, 문서가 함께 놓인 창작용 작업대

### 4.2 컬러 방향

너무 밝고 평평한 SaaS 색감은 피하고, 따뜻한 중성톤 + 기술적 포인트 컬러를 사용한다.

#### 권장 팔레트 방향

- 기본 배경: `sand`, `linen`, `fog`
- 표면 카드: `chalk`, `bone`, `mist`
- 텍스트: `ink`, `graphite`
- 정보 강조: `steel blue`
- 성공: `teal`
- 경고: `amber`
- 위험: `oxide red`

#### 권장 CSS 변수 예시

```css
:root {
  --bg-page: #f6f3ec;
  --bg-surface: #fcfaf6;
  --bg-panel: #ece7dc;
  --bg-elevated: #fffdf9;
  --fg-primary: #181b1f;
  --fg-secondary: #55606b;
  --line-soft: #ddd6c7;
  --line-strong: #b7ae9e;
  --accent-info: #3e6f8d;
  --accent-success: #2d7867;
  --accent-warning: #b97a26;
  --accent-danger: #a14737;
}
```

> **비고**: 위 팔레트는 사용자용 제품 화면 기준이다. 관리자 콘솔(`docs/admin-design-definition-v0.1.md`)은 더 차분하고 기술적인 인상을 위해 배경색 등이 미세하게 조정된 별도 팔레트를 사용하며, 최종 기준값은 디자인 시스템 토큰 문서에서 통합 확정한다.

### 4.3 배경과 레이어

- 단색 배경만 쓰지 않는다.
- 매우 약한 그리드, 노이즈, 라디얼 그라디언트, 종이 질감 같은 분위기를 조심스럽게 사용할 수 있다.
- 중요한 작업 영역은 배경보다 밝고 선명한 레이어로 띄운다.

### 4.4 타이포그래피

- 헤드라인: `Space Grotesk` 또는 `Manrope`
- 본문: `IBM Plex Sans` 또는 `Public Sans`
- 코드/로그/터미널: `JetBrains Mono` 또는 `IBM Plex Mono`

#### 원칙

- 제품은 기술적이지만 읽기 쉬워야 한다.
- 화면마다 제목, 보조설명, 상태, 메타정보 위계가 분명해야 한다.

## 5. 사용자용 레이아웃 원칙

### 5.1 기본 구조

데스크톱 기준으로 `3영역 워크스페이스`를 기본 구조로 본다.

```text
┌──────────────────────────────────────────────────────────────┐
│ Top Bar: workspace switch / search / alerts / model status  │
└──────────────────────────────────────────────────────────────┘

┌──────────────┬────────────────────────────────┬──────────────┐
│ Left Rail    │ Main Work Canvas              │ Right Rail   │
│              │                                │              │
│ chats        │ chat / project / browser /    │ context      │
│ projects     │ terminal / docs / logs        │ settings      │
│ docs         │                                │ artifacts     │
│ agents       │                                │ session info  │
└──────────────┴────────────────────────────────┴──────────────┘
```

### 5.2 중심축

- 채팅은 `입구`
- 프로젝트는 `작업 중심`
- Browser + Computer는 `실행 중심`

즉, 화면 구조도 채팅만 강조하면 안 되고, 실행 패널과 프로젝트 연결감이 함께 느껴져야 한다.

### 5.3 주요 작업 공간 패턴

- Chat-first canvas
- Project dashboard canvas
- Browser + Terminal split canvas
- Document editor canvas

## 6. 핵심 UX 구조

### 6.1 채팅에서 실행으로 이어지는 흐름

- 사용자는 채팅에서 작업을 지시한다.
- 작업 모드(`대화`, `리서치`, `개발`, `테스트`)가 명확히 드러나야 한다.
- 채팅 결과가 브라우저 세션, 프로젝트 실행, 문서화로 이어지는 경로가 가시적이어야 한다.

### 6.2 프로젝트 중심 흐름

- 프로젝트는 문서, 세션, 에이전트 실행, 테스트 결과를 묶는 허브다.
- 사용자는 프로젝트 안에서 현재 상태와 최근 작업을 직관적으로 이해할 수 있어야 한다.

### 6.3 브라우저 중심 검증 흐름

- AI가 실제로 브라우저에서 테스트하고 있다는 사실이 디자인의 핵심이다.
- 브라우저 화면은 단순 프리뷰가 아니라, `AI가 일하고 있는 창`처럼 느껴져야 한다.

### 6.4 Enterprise-Readable Trust UX

- 사용자용 화면에서도 현재 작업의 `적용 범위(personal/team/organization)`, `정책 제한`, `승인 필요 여부`, `보존 상태`가 읽혀야 한다.
- 고위험 액션은 단순 차단이 아니라 `왜 제한되었는지`, `누가 승인 가능한지`, `무엇이 기록되는지`를 설명해야 한다.
- 정책 정보는 화면을 과도하게 무겁게 만들지 않도록 badge, inline notice, detail drawer로 점진적으로 노출한다.
- 엔터프라이즈 사용자도 개발자가 아니더라도 이해할 수 있게 기술 용어와 운영 용어를 함께 사용한다.

## 7. 화면별 디자인 방향

### 7.1 랜딩 페이지

#### 목표

- 일반 AI 챗 서비스가 아니라 실행형 플랫폼이라는 차별점을 즉시 전달

#### 보여줘야 할 것

- 모델 선택 + 채팅
- Computer 세션
- 브라우저 화면
- 프로젝트 개발 흐름
- 팀 협업 가치

#### 비주얼 톤

- 제품 스크린이 핵심 hero가 되어야 함
- 텍스트보다 `실제 작업 장면`을 보여주는 편이 중요

### 7.2 홈 / 실행 대시보드

#### 목표

- 최근 채팅보다 `지금 이어서 할 일`이 먼저 보이게

#### 우선 정보

- 진행 중인 Computer 세션
- 최근 에이전트 실행
- 최근 프로젝트
- 최근 브라우저 테스트 결과

#### 디자인 포인트

- 대시보드가 정적인 목록이 아니라 `작업 재진입 허브`로 느껴져야 함

### 7.3 AI 채팅 메인

#### 목표

- 일반 대화와 실행형 작업 지시가 같은 흐름 안에 있도록 설계

#### 필수 요소

- 모델 선택기
- 작업 모드 스위치
- 메시지 리스트
- 컨텍스트 패널
- 파일 첨부
- 실행 진입 CTA

#### 디자인 포인트

- 메시지 영역은 익숙하되, `작업으로 전환되는 UI`가 분명해야 함
- 코드, 로그, 파일 변경, 결과 링크가 자연스럽게 메시지 안에 섞여야 함
- 모델 선택기에서는 `chat`, `coding`, `reasoning`, `research` 적합성 badge와 현재 제한 사유를 함께 보여줘 사용자가 추론 가능 여부가 해제된 것인지, 플랜/정책/모델 제약인지 바로 이해할 수 있어야 함

### 7.4 프로젝트 상세

#### 목표

- 프로젝트가 이 서비스의 진짜 허브처럼 보여야 함

#### 필수 요소

- 프로젝트 헤더
- 연결 문서
- 최근 세션
- 최근 브라우저 테스트
- 에이전트 실행 기록
- 멤버/소유 범위
- 결과물 보존/공유 상태 요약

#### 디자인 포인트

- Notion 문서 허브나 Git 프로젝트 페이지처럼 보이기보다, `AI와 함께 작업하는 프로젝트 공간`처럼 보여야 함
- 소유 범위, 공유 범위, 장기 보관 자산과 임시 artifact의 차이가 헤더나 메타 영역에서 읽혀야 함

### 7.5 Computer + Browser 세션

#### 목표

- 제품의 가장 강한 차별점을 전달

#### 필수 요소

- 브라우저 라이브 뷰
- 터미널
- 로그 패널
- 앱 프리뷰
- 액션 타임라인
- 상태/자원 정보
- 승인 상태와 정책 제한 안내
- artifact 보존/저장 상태 표시

#### 디자인 포인트

- 브라우저가 가장 시각적으로 중요해야 함
- 터미널과 로그는 보조지만 항상 근처에 있어야 함
- 너무 IDE처럼만 보이면 안 되고, AI 작업 과정이 읽히는 구조여야 함
- 엔터프라이즈 환경에서도 `현재 세션 범위`, `승인 필요 액션`, `보존 기간`을 숨기지 않고 명확히 보여줘야 함

### 7.6 문서 편집기

#### 목표

- 공유/댓글/버전 기반 협업을 지원하는 AI 보조 문서 작업 공간 역할 수행

#### 필수 요소

- 에디터
- 아웃라인
- 문서 메타/공유 상태 표시
- 댓글/리뷰
- AI 도우미 패널

#### 디자인 포인트

- 문서가 단순 메모장이 아니라 프로젝트 맥락과 연결된 자산처럼 보여야 함
- 실행 중 생성된 artifact와 장기 보관되는 문서/파일 자산의 상태 차이가 UI에서 읽혀야 함

### 7.7 팀 개요

#### 목표

- 팀의 실행 현황과 협업 상태를 빠르게 파악

#### 필수 요소

- 팀 프로젝트
- 공유 세션
- 최근 문서 활동
- 팀 사용량
- 멤버 상태
- 팀 공지/정책 변화 알림

#### 디자인 포인트

- 일반 팀 관리 SaaS보다 더 `작업 중심`으로 보여야 함
- 팀 범위 정책, 승인 대기, 플랜 제한 같은 운영 정보도 협업 정보와 함께 자연스럽게 보여야 함

### 7.8 플랜 / 사용량

#### 목표

- 단순 요금제가 아니라 실행 리소스 구조를 이해시키기

#### 필수 요소

- 현재 플랜
- 모델 사용량
- Computer 사용 시간
- Browser 세션 한도
- 좌석 수
- 업그레이드 CTA
- 제한 이유와 적용 범위 설명

#### 디자인 포인트

- 숫자만 나열하지 말고 `무엇이 가능하고 무엇이 제한되는지` 직관적으로 보여줘야 함
- 개인/팀/엔터프라이즈에 따라 어떤 정책이 적용되는지와 제한 사유가 설명 가능해야 함

## 8. 핵심 컴포넌트 패턴

### 8.1 Model Selector

- 단순 드롭다운이 아니라 현재 작업 목적과 연결된 선택 UI가 좋다.
- 예: `Chat`, `Code`, `Research`, `Test` 태그와 함께 표시

### 8.2 Mode Switch

- `대화 / 리서치 / 개발 / 테스트` 모드는 강한 세그먼트 컨트롤 또는 탭 형태 추천

### 8.3 Session Card

- 상태, 시작 시각, 프로젝트, 마지막 액션, 브라우저 상태를 함께 보여줌

### 8.4 Browser Canvas

- 실제 브라우저 창처럼 보여야 함
- 주소 영역, 탭, 상태 표시를 과도하게 장난스럽지 않게 표현 가능

### 8.5 Action Timeline

- AI가 검색/클릭/입력/실행/수정한 흐름을 시간축으로 보여줌

### 8.6 Artifact Card

- 로그, 테스트 결과, 스크린샷, diff 결과를 재사용 가능한 카드로 표현
- 임시 execution artifact인지, 프로젝트/문서 자산으로 저장된 결과인지 상태를 구분해 보여줌

### 8.7 Sticky Composer

- 채팅 입력창은 작업 지시 도구로도 쓰이므로 하단 고정 구조가 적합

### 8.8 Scope Badge

- 현재 리소스가 `Personal`, `Team`, `Organization` 중 어디 범위인지 즉시 이해할 수 있어야 함
- 프로젝트/문서/세션/결과물 화면에서 일관된 위치와 시각 규칙을 가져야 함

### 8.9 Policy / Approval Notice

- 현재 정책 제한, 승인 필요 여부, 승인 대기 상태를 짧은 문장과 badge로 설명
- 더 자세한 이유와 영향 범위는 drawer 또는 detail panel로 확장 가능해야 함

### 8.10 Retention / Asset Status Badge

- 결과물이 임시 artifact인지, 장기 보관 자산인지, 언제 만료되거나 정리되는지 표시 가능해야 함
- 다운로드/저장/프로젝트 반영 액션과 같은 영역에서 자연스럽게 보여야 함

## 10. 인터랙션 및 모션

- 세션 복구 시 상태 전환 피드백
- 테스트 성공/실패 결과 reveal

- 메신저 앱 같은 캐주얼 튀는 애니메이션
- 위험 상황을 가볍게 보이게 만드는 playful animation

## 11. 반응형 원칙

### 11.1 데스크톱

- 핵심 사용 환경
- 3영역 워크스페이스 적극 활용
- Browser + Terminal + Logs 동시 노출 가능

### 11.2 태블릿

- 우측 컨텍스트 패널은 접이식 또는 드로어 전환
- Browser와 Terminal은 탭 전환 가능

### 11.3 모바일

- 모든 기능 접근은 가능해야 함
- 다만 Browser / Terminal / Logs / Artifacts는 탭 구조로 전환
- 사이드바는 드로어
- 문서 편집은 읽기/편집/댓글 모드 분리 가능

#### 원칙

- 모바일에서도 핵심 흐름은 유지하되, 복잡한 병렬 정보는 단계적으로 나눠 보여준다.

## 12. 디자인 시스템 토큰 방향

### spacing

### radius

- 카드: `18px`

- 세션 패널: `20px`

## 15. 결론

이 서비스의 디자인은 `채팅`보다 `실행`, `답변`보다 `작업 과정`, `단일 화면`보다 `워크스페이스 경험`을 중심으로 설계되어야 한다.

따라서 다음 원칙을 확정한다.

- 제품은 AI 채팅 앱이 아니라 실행형 AI 작업 공간처럼 보여야 한다.
- Browser와 Computer는 핵심 시각 요소다.
- 프로젝트는 문서, 채팅, 실행, 테스트를 묶는 중심 허브다.
- 모바일까지 대응하되, 데스크톱에서 가장 강력한 경험을 제공해야 한다.
- 개인/팀/엔터프라이즈 모두가 이해 가능한 권한, 승인, 보존, 정책 가시성을 가져야 한다.
