# Computer + Browser + Agent 생명주기 정의서 v0.1

## 1. 문서 개요

- **문서명**: 실행형 AI 개발 플랫폼 Computer + Browser + Agent 생명주기 정의서
- **버전**: v0.1
- **목적**: 사용자가 작업을 요청한 시점부터 Computer 세션, 브라우저 세션, 에이전트 실행, 결과 저장, 재개, 종료까지의 흐름을 정의한다.
- **관련 문서**: `docs/product-vision-v0.1.md`, `docs/screen-list-definition-v0.2.md`, `docs/permission-plan-matrix-v0.1.md`, `docs/admin-panel-spec-v0.1.md`

---

## 2. 문서 목적

이 문서는 실행형 AI 플랫폼의 핵심 차별점인 `Computer + Browser + Agent` 흐름을 명확히 정의하기 위한 문서다. 일반 채팅과 달리 실행형 작업은 인프라, 보안, 로그, 복원, 승인, 사용량 정책이 함께 맞물려야 한다. 따라서 화면 정의와 별도로 생명주기를 독립 문서로 관리해야 한다.

---

## 3. 핵심 개념

| 개념 | 설명 |
|---|---|
| Project | 코드, 설정, 문서, 실행 기록이 연결되는 작업 단위 |
| Task Request | 사용자가 채팅 또는 에이전트 센터에서 입력한 작업 요청 |
| Execution Mode | 일반 대화, 리서치, 개발, 테스트 등 실행 방식 |
| Computer Session | 격리된 Linux 기반 실행 환경 |
| Browser Session | Chrome 기반 브라우저 실행 환경 및 라이브 뷰 |
| Agent Run | 모델이 도구를 사용하며 실제 작업을 수행하는 실행 단위 |
| Approval Gate | 특정 액션 전 사용자 또는 관리자 승인을 요구하는 단계 |
| Artifact | 로그, 스크린샷, 테스트 결과, 파일 변경, 요약 등 산출물 |
| Persistent Storage | 프로젝트 파일, 문서, 결과물을 장기 저장하는 계층 |
| Execution Node | 실제 컨테이너를 실행하는 독립 서버 또는 서버 풀 |

---

## 4. 고수준 흐름

```text
사용자 요청
-> 작업 모드 결정
-> 권한/플랜/사용량 확인
-> Computer 세션 할당
-> 프로젝트 파일 복원
-> Browser 세션 시작
-> Agent 실행
-> 코드/리서치/테스트 수행
-> 로그/브라우저 화면/결과물 기록
-> 결과 저장 및 요약
-> 세션 종료 또는 재개 대기
```

## 5. 실행 모드 정의

| 모드 | 설명 | 주요 리소스 |
|---|---|---|
| Conversation Mode | 일반 채팅 응답 중심 | 모델 호출 |
| Research Mode | 브라우저 검색/탐색/정리 중심 | Browser + Agent |
| Development Mode | 코드 수정, 실행, 디버깅 중심 | Computer + Browser + Agent |
| Test Mode | 브라우저 검증, 콘솔 확인, 회귀 확인 중심 | Browser + Computer |

## 6. 상세 생명주기

### 6.1 작업 요청 접수

- 사용자는 모델, 프로젝트, 작업 모드, 컨텍스트를 선택한다.
- 요청은 채팅 화면 또는 에이전트 센터에서 시작될 수 있다.
- 시스템은 요청이 단순 응답으로 끝나는지, 실행형 세션이 필요한지 판단한다.
- 이때 결정된 `Execution Mode`는 이후 `execution_queue_item`, `agent_run`, `computer_session`에 일관되게 기록한다.

### 6.2 권한 및 자원 검사

- 현재 사용자의 역할과 워크스페이스 범위를 검사한다.
- 플랜 entitlement와 사용량 한도를 확인한다.
- 동시 세션 수, 브라우저 사용 가능 여부, 고급 모델 접근 가능 여부를 검사한다.
- 조건을 충족하지 못하면 세션 생성 대신 업그레이드/대기/권한 오류 흐름으로 전환한다.

### 6.3 Computer 세션 준비

- 시스템은 사용 가능한 Execution Node를 선택한다.
- 프로젝트 유형에 맞는 런타임 템플릿(Node, Python, Java 등)을 결정한다.
- 컨테이너를 생성하고 Persistent Storage를 마운트한다.
- 이전 세션 기록이 있으면 프로젝트 파일과 필요한 메타데이터를 복원한다.
- 필요한 경우 기본 의존성 설치 단계를 준비한다.

### 6.4 Browser 세션 준비

- 브라우저가 필요한 작업인 경우 Chrome 세션을 시작한다.
- 브라우저 세션은 Computer 세션과 연결되어야 하며, 사용자는 라이브 뷰를 볼 수 있어야 한다.
- 세션 정책에 따라 외부 사이트 접근, 로그인 가능 여부, 파일 업로드 가능 여부가 결정된다.
- `browser_requested=true`였지만 아직 준비 중인 상태와, 애초에 브라우저가 필요 없어서 요청하지 않은 상태는 구분해야 한다.

### 6.5 Agent 실행 시작

- Agent는 사용자의 요청, 프로젝트 컨텍스트, 문서 컨텍스트, 작업 모드에 따라 실행된다.
- Agent는 파일 읽기/수정, 명령 실행, 브라우저 탐색, 테스트 실행을 수행할 수 있다.
- 모든 작업은 타임라인과 로그로 기록된다.

### 6.6 실행 중 관찰 가능성

- 사용자는 브라우저 화면을 실시간 또는 준실시간으로 볼 수 있어야 한다.
- 터미널 로그, 파일 변경 내역, 테스트 결과가 함께 제공되어야 한다.
- 브라우저에서 어떤 페이지를 열고 어떤 액션을 수행했는지 액션 로그가 남아야 한다.

### 6.7 검증 및 테스트

- Development Mode에서는 앱 실행 후 브라우저에서 실제 미리보기를 확인한다.
- Test Mode에서는 콘솔 에러, 네트워크 실패, 렌더링 문제, 사용자 흐름 문제를 확인한다.
- 테스트 결과는 성공/실패 상태와 근거(로그, 스크린샷, 에러 메시지)로 저장된다.

### 6.8 결과 저장

- 수정된 프로젝트 파일은 Persistent Storage에 저장한다.
- 브라우저 스크린샷, 콘솔 로그, 테스트 결과, 에이전트 요약을 Artifact로 저장한다.
- 결과는 프로젝트 상세, 에이전트 실행 상세, 문서화 흐름에서 재사용할 수 있어야 한다.
- 실행 중 산출물은 기본적으로 ephemeral artifact로 저장하고, 장기 재사용이 필요한 경우 `file_asset`/`attachment`로 승격하며 보존/공유 정책을 다시 계산한다.

### 6.9 세션 종료 또는 대기

- 작업 완료 후 세션은 즉시 종료되거나, 짧은 시간 재개 가능한 `warm` 상태로 유지될 수 있다.
- 사용자는 같은 프로젝트에서 이전 세션을 재개할 수 있어야 한다.
- 장시간 비활성 세션은 자동 종료 정책을 따른다.

### 6.10 세션 재개

- 사용자가 프로젝트를 다시 열면 이전 실행 맥락을 복구한다.
- 프로젝트 파일은 항상 복원되어야 하며, 프로세스 상태는 정책에 따라 재시작될 수 있다.
- 필요한 의존성 설치와 서버 실행은 자동 또는 반자동으로 재수행될 수 있다.

### 6.11 실패 및 복구

- 컨테이너 생성 실패, 브라우저 충돌, 설치 실패, 권한 부족, 사용량 초과 등 다양한 실패 상태를 구분해야 한다.
- 실패 시 어떤 단계에서 무엇이 실패했는지 명확히 보여줘야 한다.
- 가능한 경우 재시도, 새 세션으로 재시작, 승인 요청, 플랜 업그레이드 안내로 이어진다.

### 6.12 정리 및 해제

- 종료된 세션의 컴퓨팅 리소스는 해제한다.
- 임시 프로세스, 임시 브라우저 상태, 캐시 정책에 따라 정리한다.
- 영구 저장 대상과 폐기 대상을 구분해야 한다.

## 7. 상태 모델

### 7.1 Computer Session 상태

| 상태 | 설명 |
|---|---|
| requested | 세션 생성이 요청됨 |
| queued | 실행 리소스를 기다리는 상태 |
| provisioning | 컨테이너 및 환경 생성 중 |
| restoring | 프로젝트 및 세션 정보 복원 중 |
| ready | 실행 준비 완료 |
| running | 실제 작업 수행 중 |
| paused | 일시 정지 또는 대기 상태 |
| warm | 짧은 시간 재개 가능하도록 유지되는 대기 상태 |
| stopping | 종료 처리 중 |
| completed | 정상 종료 |
| terminated | 사용자 또는 관리자에 의한 강제 종료 |
| failed | 오류로 종료 |
| expired | 정책상 만료 |

### 7.2 Browser Session 상태

| 상태 | 설명 |
|---|---|
| launching | Chrome 초기화 중 |
| ready | 사용자와 AI가 사용할 준비 완료 |
| navigating | 페이지 이동/검색 중 |
| interacting | 클릭/입력/테스트 수행 중 |
| validating | 테스트 및 검증 단계 |
| crashed | 브라우저 비정상 종료 |
| closed | 정상 종료 |

브라우저가 필요 없는 작업은 `browser_session` row를 만들지 않는 것을 기본으로 한다.

### 7.3 Agent Run 상태

| 상태 | 설명 |
|---|---|
| pending | 실행 대기 |
| waiting_for_resources | 세션/리소스 할당 대기 |
| waiting_for_approval | 사용자 승인 대기 |
| running | 작업 수행 중 |
| retrying | 실패 후 재시도 중 |
| completed | 정상 완료 |
| failed | 오류로 종료 |
| cancelled | 사용자 또는 시스템에 의해 취소 |

## 8. 승인 및 안전 정책

### 8.1 자동 허용 가능 액션

- 프로젝트 읽기
- 문서 읽기
- 일반 응답 생성
- 브라우저를 통한 일반 검색
- 로컬 개발 서버 실행

### 8.2 정책 기반 허용 액션

- 파일 생성/수정
- 패키지 설치
- 브라우저 입력/클릭 자동화
- 외부 사이트 탐색
- 테스트 실행

### 8.3 명시적 승인 필요 액션

- 파일 삭제 또는 대량 변경
- 외부 서비스 로그인
- 배포/배포 준비 액션
- 결제/청구/관리자 관련 액션
- 민감 정보 사용이 필요한 액션

### 8.4 프로젝트별 정책 확장

- 프로젝트는 `자동 실행 우선`, `승인 우선`, `엄격 모드` 같은 정책 프리셋을 가질 수 있다.
- Team/Enterprise에서는 관리자 정책이 개인 설정보다 우선할 수 있다.

## 9. 저장 및 복원 정책

### 9.1 영구 저장 대상

- 프로젝트 파일
- 문서와 연결 메타데이터
- 브라우저 스크린샷
- 테스트 결과
- 에이전트 요약
- 실행 로그 요약

### 9.2 비영구 대상

- 실행 중 프로세스 메모리
- 임시 캐시
- 일시적 브라우저 탭 상태
- 세션 내부 임시 파일 일부

### 9.3 복원 원칙

- 프로젝트 파일은 항상 복원 가능해야 한다.
- 브라우저는 필요 시 새로 띄우더라도, 직전 작업 맥락은 로그와 URL 정보로 복구 가능해야 한다.
- 세션 전체 스냅샷은 MVP에서는 선택사항이며, v1 이후 고도화 대상으로 본다.

## 11. 협업 관점 요구사항

- 팀 프로젝트에서는 다른 팀원이 실행 상세를 조회할 수 있어야 한다.
- 팀 단위로 최근 실행 세션과 테스트 결과를 공유할 수 있어야 한다.
- 추후에는 세션 관전, 코멘트, 인수인계, 재실행 권한을 세분화할 수 있어야 한다.

---

## 12. 사용량 및 과금 연동 지점

- 세션 생성 시점에 동시 세션 수를 체크한다.
- 세션 실행 중 Computer Runtime과 Browser Runtime을 누적한다.
- 에이전트 실행 수와 모델 사용량을 별도 집계한다.
- 멀티에이전트/워크플로우는 별도 과금 단위로 확장 가능해야 한다.

---

## 13. MVP 범위

- 단일 Computer 세션 생성/재개/종료

- 기본 테스트 결과 저장
