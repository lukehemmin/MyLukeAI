# 권한 및 플랜 매트릭스 정의서 v0.1

## 1. 문서 개요

- **문서명**: 실행형 AI 개발 플랫폼 권한 및 플랜 매트릭스 정의서
- **버전**: v0.1
- **목적**: 플랜, 역할, 소유 범위, 사용량 제한을 분리 정의하여 초기에는 수동 운영이 가능하고, 이후 결제 시스템을 붙여도 확장 가능한 구조를 만든다.
- **관련 문서**: `docs/product-vision-v0.1.md`, `docs/screen-list-definition-v0.2.md`, `docs/admin-panel-spec-v0.1.md`, `docs/admin-screen-definition-v0.1.md`

## 2. 기본 원칙

- **플랜**은 어떤 기능과 자원을 어느 정도까지 사용할 수 있는지를 결정한다.
- **역할(Role)**은 어떤 사용자가 어떤 리소스를 관리할 수 있는지를 결정한다.
- **워크스페이스 범위(Scope)**는 리소스가 개인 소유인지, 팀 소유인지, 조직 소유인지를 결정한다.
- **과금 구조**는 나중에 붙여도 되지만, `Billing Account`, `Subscription`, `Entitlement`, `Usage Record` 구조는 처음부터 분리 설계한다.
- 실행형 기능은 채팅 기능과 별도로 `Computer 사용 시간`, `브라우저 세션`, `동시 실행 수`, `스토리지`, `에이전트 실행 수`를 계량할 수 있어야 한다.
- UI/UX는 단순히 허용/차단만 보여주는 것이 아니라, 현재 유효 권한과 정책 적용 범위를 설명 가능해야 한다.

## 3. 워크스페이스 유형

| 워크스페이스 유형 | 설명 | 기본 소유 범위 |
|---|---|---|
| Personal Workspace | 개인 사용자가 단독으로 사용하는 작업 공간 | 사용자 본인 |
| Team Workspace | 팀원이 공동으로 문서/프로젝트/실행 기록을 공유하는 공간 | 팀 |
| Enterprise Workspace | 조직 정책과 보안 제어가 강화된 팀/조직 공간 | 조직 |

비고:

- API 레이어에서는 협업 리소스가 `teamId`, 사용량/과금 리소스가 연결된 `workspaceId`를 사용할 수 있다.
- 즉 Team Workspace는 팀과 강하게 연결되지만, 협업 식별자와 자산/과금 식별자는 구분될 수 있다.

### 3.1 그룹(Group) 개념

- `Group`은 팀 워크스페이스와 다른 개념이며, 관리자에 의해 운영되는 `접근 제어 및 기본 정책 묶음`이다.
- 그룹은 사용자 집합에 기본 모델, 기능 접근 권한, 공유 정책, 업로드 정책 등을 부여하는 데 사용한다.
- 사용자는 개인/팀 워크스페이스에 속할 수 있고, 동시에 하나 이상의 그룹 정책을 적용받을 수 있다.
- 즉, `Team`은 협업 단위이고 `Group`은 권한/정책 단위다.

## 7. 역할 정의

| 역할 | 범위 | 설명 |
|---|---|---|
| Personal User | 개인 워크스페이스 | 개인 자산 생성/실행/관리 |
| Team Member | 팀 워크스페이스 | 팀 자산 사용 및 공동 작업 |
| Team Admin | 팀 워크스페이스 | 팀원, 공용 자산, 사용량 일부 관리 |

### 7.1 관리자 세분 권한

- `Platform Admin`은 전역 운영 관리자의 상위 개념이다.
- 실제 운영에서는 아래처럼 세분화된 관리자 역할을 둘 수 있으며, 이들은 `Platform Admin`의 제한된 하위 권한 세트로 본다.

| 세부 관리자 역할 | 설명 |
|---|---|
| Super Admin | 모든 전역 운영 권한과 최고 보안/복원 권한 보유 |
| Support Admin | 사용자/팀 지원과 기본 운영 조치 중심 |
| Billing Admin | 플랜, 좌석, 사용량, 청구 관련 운영 중심 |
| Security Admin | SSO, 감사, 시크릿, 접근 제어 정책 운영 중심 |

## 9. 소유권 및 리소스 범위 규칙

### 9.1 개인 리소스

- 개인 워크스페이스에서 생성된 프로젝트, 문서, 실행 기록은 사용자 소유다.
- 개인 리소스는 기본적으로 다른 사용자에게 보이지 않는다.
- 개인 리소스를 팀으로 옮기려면 명시적 `복제` 또는 `이전` 액션이 필요하다.

### 9.2 팀 리소스

- 팀 워크스페이스에서 생성된 프로젝트, 문서, 실행 기록은 개인이 아닌 팀 소유다.
- 작성자가 팀을 떠나더라도 팀 리소스는 팀에 남는다.
- 팀원은 권한에 따라 팀 리소스를 조회/수정/실행할 수 있다.

### 9.3 실행 결과물

- Computer 세션 산출물, 브라우저 스크린샷, 테스트 로그, 에이전트 결과물은 연결된 프로젝트 또는 워크스페이스 범위를 상속한다.
- 개인 프로젝트에서 실행된 결과는 개인 범위에 저장된다.
- 팀 프로젝트에서 실행된 결과는 팀 범위에 저장된다.

## 11. 팀 초대 및 좌석 정책

- Team/Enterprise 플랜에서만 팀 초대가 가능하다.
- 초대 가능한 인원 수는 좌석 수와 연결된다.
- 초대 대기 상태도 좌석 점유 여부를 정책적으로 정의해야 한다.
- 팀 탈퇴 또는 멤버 제거 시 좌석이 반환된다.
- Owner는 좌석 부족 시 플랜 업그레이드 또는 운영자 문의 흐름으로 이동한다.

---

## 12. 청구 구조 기본안

### 12.1 Billing Account

- 개인은 사용자 계정이 Billing Account의 주체가 된다.
- 팀은 Team Workspace가 Billing Account의 주체가 된다.
- 엔터프라이즈는 조직 또는 계약 단위가 Billing Account의 주체가 된다.

### 12.2 Subscription

- 현재 활성 플랜과 계약 상태를 기록한다.
- 결제 시스템 미도입 시에도 운영자가 수동으로 플랜을 부여할 수 있어야 한다.

### 12.3 Entitlement

- 실제 기능 접근 권한과 사용량 한도를 정의한다.
- 플랜 자체와 분리하여 프로모션, 수동 조정, 엔터프라이즈 커스텀 구성이 가능해야 한다.

### 12.4 Usage Record

- 토큰, 실행 시간, 스토리지, 좌석, 오케스트레이션 실행 수 등을 누적/조회할 수 있어야 한다.

## 13. 제한 적용 시점

- 세션 생성 전: 동시 세션 수, 권한, 플랜 허용 여부 검사
- 세션 실행 중: 시간 한도, 리소스 사용량, 정책 위반 여부 검사
- 멤버 초대 시: 좌석 수 검사
- 스토리지 증가 시: 플랜 한도 검사
- 멀티에이전트/워크플로우 실행 전: 플랜 entitlement 검사

### 13.1 UI/UX 노출 원칙

- 권한 화면은 `현재 내 역할`, `적용 범위`, `상속/override 여부`, `관리 가능한 액션`을 함께 보여줘야 한다.
- 사용량/플랜 화면은 단순 숫자 나열이 아니라 `어떤 entitlement 때문에 제한되는지`를 설명해야 한다.
- 모델 선택 UI는 추론이 단순히 꺼진 것처럼 보이지 않도록 `플랜 제한`, `정책 제한`, `provider 미지원`, `role mismatch`를 구분해 보여줘야 한다.
- 승인 기반 액션 화면은 `왜 승인 필요한지`, `누가 승인 가능한지`, `어떤 로그가 남는지`를 보여줘야 한다.
- 엔터프라이즈 보안 화면은 SSO, 감사, 데이터 보존 정책을 같은 거버넌스 맥락 안에서 읽을 수 있어야 한다.
