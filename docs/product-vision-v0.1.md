## 2. 한 줄 정의

우리 제품은 다양한 AI 모델을 선택해 대화할 수 있을 뿐 아니라, AI가 실제 Computer와 브라우저를 사용해 리서치, 풀스택 개발, 실행, 테스트까지 수행하는 **실행형 AI 개발 플랫폼**이다.

---

## 3. 제품 소개

이 제품은 일반적인 AI 채팅 서비스처럼 모델과 대화하는 기능을 제공하지만, 그 수준에서 멈추지 않는다. 사용자는 원하는 AI 모델을 선택해 질문하거나 작업을 지시할 수 있고, 필요할 경우 AI는 격리된 Linux 기반 Computer 세션과 Chrome 브라우저 화면을 사용해 실제로 검색하고, 조사하고, 코드를 작성하고, 프로젝트를 실행하고, 브라우저에서 테스트할 수 있다.

핵심은 사용자가 단순히 결과만 받는 것이 아니라, AI가 어떤 과정을 통해 결과를 만들어내는지를 직접 확인할 수 있다는 점이다. 이 플랫폼은 채팅형 AI, 실행형 AI, 개발형 AI를 하나의 서비스 안에서 연결하는 것을 목표로 한다.

제품 구조도 이 목표에 맞춰 분리된다. 사용자 웹앱과 관리자 콘솔은 `control plane`, Computer/Browser/Agent 실행은 `execution plane`, 파일/이미지/artifact 보관은 `storage plane`으로 나뉘며, 운영 정책은 관리자 UI를 canonical control surface / write path로, Postgres를 persisted canonical data / source of truth로 삼는다.

## 4. 해결하려는 문제

### 4.1 일반 AI 채팅 서비스의 한계

- 많은 AI 서비스는 답변 생성에는 강하지만, 실제 실행과 검증까지 이어지지 않는다.
- 사용자는 코드나 제안을 받더라도 직접 실행, 테스트, 디버깅을 다시 해야 한다.
- 브라우저에서 실제로 동작하는지 확인하는 과정이 서비스 밖에서 분리되어 있다.

### 4.2 실행형 도구의 한계

- 일부 실행형 AI 도구는 작업 수행이 가능하지만, 모델 선택 폭이 제한적이거나 특정 사용 시나리오에 치우쳐 있다.
- 어떤 작업을 했는지 사용자에게 충분히 가시적으로 보여주지 못하는 경우가 있다.
- 결과물, 로그, 브라우저 테스트, 프로젝트 자산이 하나의 작업 흐름으로 연결되지 않는 경우가 많다.

### 4.3 팀 개발 환경의 단절

- 리서치, 문서, 프로젝트, 실행 환경, 테스트 결과가 서로 다른 도구에 분산되어 있다.
- 팀 단위로 AI를 활용할 때 권한, 좌석, 사용량, 공용 프로젝트, 공용 문서를 함께 관리하기 어렵다.
- 초기에는 결제가 없어도 되지만, 나중에 바로 상용화할 수 있는 구조가 필요한 경우가 많다.

## 5. 우리가 만들고자 하는 핵심 경험

### 5.1 모델 선택 자유도

- 사용자는 작업 목적에 따라 모델을 선택할 수 있어야 한다.
- OpenAI, Anthropic, Google 계열을 포함해 다양한 모델 공급자를 유연하게 확장할 수 있어야 한다.
- 일반 대화, 코딩, 추론, 리서치, 분석 등 작업 성격에 따라 최적 모델을 쓸 수 있어야 한다.

### 5.2 대화에서 실행으로 자연스럽게 전환

- 사용자는 채팅에서 바로 작업을 지시할 수 있어야 한다.
- 같은 요청이 필요에 따라 일반 응답, 브라우저 리서치, Computer 기반 개발 실행으로 이어질 수 있어야 한다.
- 채팅은 제품의 입구이며, 실행은 제품의 본체라는 구조를 가져야 한다.

### 5.3 AI가 실제로 일하는 화면을 보여주는 경험

- AI는 Computer 세션에서 명령을 실행하고 파일을 수정할 수 있어야 한다.
- AI는 Chrome 화면을 통해 검색, 탐색, 테스트를 수행할 수 있어야 한다.
- 사용자는 브라우저 화면, 액션 로그, 실행 로그, 결과물을 함께 보며 작업 과정을 이해할 수 있어야 한다.

### 5.4 브라우저 기반 검증 경험

- 풀스택 개발 결과는 실제 브라우저에서 검증되어야 한다.
- AI는 단순히 서버를 실행하는 것이 아니라, 브라우저에서 동작 여부를 확인해야 한다.
- 사용자는 실제 사용자처럼 테스트된 결과를 받는다는 신뢰를 가져야 한다.

### 5.5 프로젝트 중심 협업 경험

- 채팅, 문서, 에이전트, Computer 세션, 브라우저 테스트는 모두 프로젝트 중심으로 연결되어야 한다.
- 개인뿐 아니라 팀도 공동 프로젝트, 공동 문서, 공용 실행 기록을 공유할 수 있어야 한다.
- 팀 플랜은 단순 좌석 판매가 아니라 협업 가치가 분명해야 한다.

### 5.6 결과가 프로젝트 자산으로 누적되는 경험

- 브라우저 스크린샷, 테스트 리포트, 실행 로그 요약, export 결과물은 실행 중에는 artifact로 남고, 필요 시 프로젝트/문서/채팅 자산으로 승격되어 재사용될 수 있어야 한다.
- 사용자는 어떤 결과가 일시적 실행 산출물인지, 어떤 결과가 장기 보관되는 파일/문서 자산인지 구분할 수 있어야 한다.
- 실행 결과가 사라지지 않고 프로젝트 맥락 안에 축적되어야 팀 협업과 재실행 가치가 생긴다.

### 5.7 엔터프라이즈에서도 신뢰할 수 있는 경험

- 이 제품은 개발자 전용 도구처럼만 보이면 안 되고, 개인 사용자부터 팀, 엔터프라이즈 운영 조직까지 이해 가능한 UX를 가져야 한다.
- 감사 로그, SSO, 권한, 데이터 보존, 정책 적용 범위, 승인 흐름은 숨은 설정이 아니라 제품 신뢰를 만드는 핵심 UX로 드러나야 한다.
- 사용자는 어떤 액션이 허용되었는지뿐 아니라, 어떤 정책 때문에 제한되었는지와 어떤 승인 체인을 거치는지도 이해할 수 있어야 한다.
- 관리자와 엔터프라이즈 운영자는 `누가`, `무엇을`, `어느 범위에`, `왜` 바꾸거나 승인했는지 즉시 파악할 수 있어야 한다.

## 6. 핵심 제품 원칙

- **Execution First**: 핵심 가치는 답변 생성이 아니라 실제 작업 수행과 검증에 있다.
- **Model Agnostic**: 특정 모델에 종속되지 않고 다양한 모델을 작업에 맞게 선택할 수 있어야 한다.
- **Browser-Grounded Validation**: 브라우저 기반 테스트와 검증은 핵심 UX다.
- **Project-Centric Work**: 채팅, 문서, 에이전트, 실행은 프로젝트를 중심으로 연결된다.
- **Visible and Auditable Actions**: AI의 행동은 브라우저 화면, 로그, 변경 이력으로 추적 가능해야 한다.
- **Governance-Visible UX**: 권한, 승인, 정책 적용 범위, 데이터 보존, 감사 가능성이 UI에서 명확히 읽혀야 한다.
- **Separated Planes, Connected Experience**: control plane, execution plane, storage plane은 분리되지만 사용자 경험은 하나로 이어져야 한다.
- **Team-Ready Architecture**: 처음부터 개인/팀/엔터프라이즈 확장이 가능한 구조여야 한다.
- **Monetization-Ready Foundation**: 결제는 나중에 붙여도 플랜/권한/사용량 구조는 먼저 준비되어야 한다.

## 8. 대표 사용 시나리오

### 8.1 리서치 시나리오

- 사용자는 모델을 선택하고 조사할 주제를 입력한다.
- AI는 브라우저를 열고 검색, 탐색, 비교, 정리를 수행한다.
- 사용자는 AI가 어떤 페이지를 보고 무엇을 근거로 정리하는지 확인한다.
- 결과는 문서나 프로젝트 노트로 저장된다.

### 8.2 풀스택 개발 시나리오

- 사용자는 프로젝트를 생성하고 개발 요청을 입력한다.
- AI는 Computer 세션에서 코드를 작성하고 의존성을 설치하고 앱을 실행한다.
- AI는 Chrome 화면에서 실제 UI를 열어 동작을 테스트한다.
- 사용자는 브라우저 검증 결과, 로그, 변경 파일을 확인하고 다음 작업을 지시한다.

### 8.3 디버깅 시나리오

- 사용자는 오류 상황이나 재현 단계를 전달한다.
- AI는 프로젝트를 실행하고 로그/콘솔/브라우저 동작을 분석한다.
- AI는 문제 원인을 찾아 수정한 뒤 다시 실행해 검증한다.
- 사용자는 수정 전후 차이와 테스트 결과를 확인한다.

### 8.4 팀 협업 시나리오

- 팀은 하나의 워크스페이스에서 프로젝트와 문서를 공유한다.
- 팀원은 같은 프로젝트를 기준으로 대화, 실행 기록, 테스트 결과를 함께 본다.
- 팀 관리자는 좌석, 사용량, 공용 리소스를 관리한다.
- 팀은 에이전트와 실행 환경을 공동 생산성 도구처럼 활용한다.

### 8.5 엔터프라이즈 운영 시나리오

- 엔터프라이즈 관리자는 SSO, 권한, 그룹 정책, 데이터 보존, 브라우저/에이전트 승인 정책을 운영한다.
- 보안 담당자는 감사 로그와 승인 이력을 통해 누가 어떤 변경과 실행을 했는지 추적한다.
- 팀 사용자는 실행 화면 안에서 현재 정책 범위, 승인 필요 여부, 결과물 보존 상태를 이해한 채 작업을 이어간다.

## 9. 제품 포지셔닝

### 9.1 참조 가능한 제품 성격

- `OpenWebUI` 계열의 멀티 모델 AI 채팅 경험
- `Manus` 계열의 실행형 AI 작업 경험
- `Z.ai` 계열의 풀스택 개발/실행/테스트 경험

### 9.2 우리 제품의 포지셔닝

우리는 위 세 가지 감각을 하나로 합치되, 단순 참고 수준이 아니라 **채팅 + 실행 + 브라우저 검증 + 프로젝트 협업**을 일관된 제품 구조로 통합하는 것을 목표로 한다.

### 9.3 차별점

- 하나의 제품 안에서 대화형 AI와 실행형 AI를 모두 제공한다.
- AI의 브라우저 작업 과정을 사용자에게 시각적으로 보여준다.
- 프로젝트 중심으로 문서, 실행, 테스트, 에이전트 결과를 연결한다.
- 개인 사용자부터 팀/엔터프라이즈까지 확장 가능한 구조를 가진다.
- 결제 도입 전에도 플랜/권한/사용량 제어가 가능한 SaaS 기반을 갖춘다.

## 14. 서비스 소개 문구 초안

### 14.1 짧은 소개 문구

AI가 답변만 하는 것이 아니라, 실제로 일하고 테스트하는 실행형 AI 개발 플랫폼

### 14.2 서비스 소개 문단 초안

우리 서비스는 다양한 AI 모델을 자유롭게 선택해 대화할 수 있는 멀티 모델 AI 환경 위에, AI가 실제 Computer와 브라우저를 사용해 리서치, 개발, 실행, 테스트까지 수행하는 실행형 작업 환경을 결합한 플랫폼이다. 사용자는 AI가 무엇을 했는지 Chrome 화면과 로그를 통해 직접 확인할 수 있으며, 프로젝트와 문서, 팀 협업 흐름 안에서 결과를 축적하고 재사용할 수 있다.
